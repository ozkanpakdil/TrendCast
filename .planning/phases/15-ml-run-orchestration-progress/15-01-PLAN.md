# Phase 15 Plan 01: Serialized ML Run Queue + requestId-Scoped Terminal States

**Requirement:** MLPROG-01 — progress always reaches a terminal state; overlapping runs queue instead of overwriting each other's resolvers; results/progress scoped by requestId.

## Tasks

### Task 1 — `src/utils/ml-run-queue.ts` (new)

Framework-free serialized queue (no browser APIs → unit-testable):

```ts
export interface MlRunEntry {
  requestId: string;
  run: () => Promise<void>;
  reject: (err: Error) => void;
}

export class MlRunQueue {
  enqueue(entry: MlRunEntry): void            // FIFO; starts immediately if idle
  cancel(requestId: string): boolean          // reject queued entry ('cancelled'); active handled by caller
  isQueued(requestId: string): boolean        // active or waiting
  get activeRequestId(): string | null
}
```

- One active run at a time; next dequeues on settle (resolve/reject).
- `cancel` on the active run returns `false` (caller terminates the worker); on queued entries rejects with `Error('Correlation cancelled by user.')`.

### Task 2 — `src/utils/ml-run-state.ts` (new)

Persisted run-state marker for MV3 service-worker death:

```ts
export interface MlRunState { requestId: string; engine: string; model: string; startedAt: number }
export async function readMlRunState(storage, key): Promise<MlRunState | null>
export async function writeMlRunState(storage, key, state): Promise<void>
export async function clearMlRunState(storage, key): Promise<void>
```

Narrow `SettingsStorage`-style interface (pick/get/set) per the v0.1.5 storage-I/O convention.

### Task 3 — Background wiring (`src/background/index.ts`)

1. Replace `mlWorkerResolvers`/`mlWorkerRequestId` singleton with `MlRunQueue`; `runMLCorrelation` enqueues; worker messages resolve/reject the active entry.
2. `cancelMLCorrelation(requestId)` — terminate worker for the active run; queue.cancel for queued ones.
3. Stamp `requestId` on **every** terminal result in `runCorrelationWithEngine` (success + ML-error return) and in `runCorrelationAsync`'s catch (error result currently unstamped).
4. Marker lifecycle: write on run start, clear on terminal (success/error/cancel); on background startup, orphaned marker → clear + broadcast `CORRELATION_RESULT` with `error: 'interrupted'` for that requestId.
5. `CANCEL_CORRELATION` handler forwards `payload.requestId`.

### Task 4 — Hook scoping (`src/dashboard/hooks/useCorrelations.ts`)

1. Ignore `CORRELATION_PROGRESS` whose `requestId` ≠ `requestIdRef.current` (precompute can't resurrect the bar).
2. While loading, poll `CORRELATION_RUN_STATE` (new message) every 5s; if background reports not-live, settle with interrupted error (SW-death path).
3. Storage-poll fallback: only accept results whose `requestId` matches the active id (drop the `!cached.requestId` acceptance for runs with an active id).

- `src/types/index.ts`: add `CORRELATION_RUN_STATE` request/response messages.
- `tests/unit/ml-run-queue.test.ts`: FIFO order, one-active, cancel-queued rejects, cancel-unknown false, isQueued, marker read/write/clear round-trip, orphan detection.
