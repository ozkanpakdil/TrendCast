Close the regression-coverage gap for the settings migration wiring and run the full regression suite as a gate.

No behavior change; no new packages.

Output: A testable storage-I/O layer for settings, integration tests proving the migration wiring backfills the new flags and preserves explicit preferences, and a green full-suite regression run.
</objective>

    In `src/utils/settings.ts`:
    - Add a minimal `SettingsStorage` interface: `{ get(keys: string): Promise<Record<string, unknown>>; set(items: Record<string, unknown>): Promise<void> }`. `browser.storage.local` satisfies this structurally (its `get` accepts a string key and returns a `Record`).

    - Add `export async function getSettingsFromStorage(storage: SettingsStorage): Promise<ExtensionSettings>` that reads `CONFIG.storage.settings` via `storage.get`, casts the value to `Partial<ExtensionSettings> | undefined`, and returns `deepMergeSettings(DEFAULT_SETTINGS, stored)`.
    - Add `export async function migrateEnabledSourcesFromStorage(storage: SettingsStorage): Promise<void>` that reads `CONFIG.storage.settings`, calls `migrateEnabledSources(stored)`, and — only when the result is non-null — writes it back via `storage.set({ [CONFIG.storage.settings]: migrated })`. When `migrateEnabledSources` returns `null`, do nothing (no write). Do NOT wrap this in try/catch — keep it a raw, testable storage I/O function.

    In `src/background/index.ts`:
    - Replace the existing `deepMergeSettings, migrateEnabledSources` import from `@/utils/settings` with `getSettingsFromStorage, migrateEnabledSourcesFromStorage` (the two old helpers become unused after delegation — keeping them would fail `bun run typecheck` under `noUnusedLocals`).
    - Replace the body of `getSettings()` (currently lines ~900-906) with `return getSettingsFromStorage(browser.storage.local);` — keep the same function name and signature so all existing call sites (`runCollection`, `runAlertSweep`, `CORRELATE_ALL`, etc.) are unchanged.
    - Replace the body of `migrateEnabledSourcesDefault()` (currently lines ~940-955) with a `try { await migrateEnabledSourcesFromStorage(browser.storage.local); } catch (err) { console.warn('[TrendCast] News source flags migration failed (non-fatal):', err); }` — preserve the existing non-fatal try/catch behavior exactly. Keep the function name and signature.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| storage → settings read | `chrome.storage.local` settings blob (untrusted/partial/corrupt) crosses into `getSettingsFromStorage` / `migrateEnabledSourcesFromStorage` |
| migration → storage write | backfilled settings written back to `chrome.storage.local` |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-13-01 | Tampering | `migrateEnabledSources` / `migrateEnabledSourcesFromStorage` | medium | mitigate | Only backfills missing keys — present keys (explicit user preferences) always win. Integration test 5 asserts an explicit `stockScreener: false` survives the write. |
| T-13-02 | Denial of Service | `migrateEnabledSourcesFromStorage` | low | mitigate | `migrateEnabledSources` returns `null` when nothing is missing, so the caller skips the write — no storage churn on every restart. Integration test 4 asserts `storage.set` is not called for a fully-populated store. |
| T-13-03 | Tampering | `deepMergeSettings` | medium | mitigate | Non-object `enabledSources` (corruption) falls back to `defaults.enabledSources` instead of spreading junk keys (already covered by existing unit tests). |
| T-13-SC | Tampering | npm/pip/cargo installs | high | accept | No new packages installed this phase — no install tasks exist, so the package-legitimacy gate is not triggered. |
</threat_model>
